## 1. Контекст и цель

### 1.1 Что есть сейчас

- **Собственная БД** с серверной частью, доступной по **gRPC**.
- **Клиентское приложение — «db-manager».** Сейчас это **POC на Flutter**
  (`ddbs_client`). POC валидировал UX и визуальный язык, но накопил долги:
  слой отображения и слой работы с данными во многих местах перемешаны, часть
  ранних подходов уже переосмыслена, но всё ещё присутствует в коде.
- **Начальный каркас на Qt** (`synaps_client`): Qt 6.10 + QML (модуль `Synaps`),
  C++20, CMake/Ninja, сборка под macOS (bundle) / Windows / Linux. Реализованы
  `AuthService` (пока mock, экспонирован в QML через `QML_SINGLETON` +
  `Q_PROPERTY`/`Q_INVOKABLE`/`Q_ENUM`), экран логина, домашний экран с наброском
  4-панельного layout. gRPC/Protobuf пока **не подключены**, асинхронности и
  логирования ещё нет.

### 1.2 Цель

Сделать **production-клиент на Qt 6 + QML** (desktop: Windows, macOS, Linux),
повторяющий функциональность и визуальный язык POC, но с **чистым разделением
слоёв** и переосмысленными ключевыми механизмами. Это требование бизнеса.

### 1.3 Где этот документ в цепочке работ

```
[ этот документ: концепция и требования ]
            │
            ▼
[ фаза архитектуры: детальный дизайн компонентов, контрактов, диаграмм ]
            │

```

### 1.4 Scope документа

**Входит:** видение; глоссарий; формализация протокола QL и 4 flow; концепции
Query / QueryManager / подписки / TabManager / разделения слоёв; функциональные и
нефункциональные требования; рекомендуемое направление архитектуры с названными
паттернами; структура экрана и список экранов; открытые вопросы.

**Не входит** (следующие фазы): детальный дизайн классов/интерфейсов/сигнатур и
диаграммы классов; поэкранная проработка каждого экрана; финальный выбор стека и
библиотек; план работ с оценками; любые изменения кода или proto.

## 2. Глоссарий (кратко)

Полный глоссарий — в [glossary.md](glossary.md). Минимум для чтения документа:

| Термин | Значение |
|---|---|
| **Query (Запрос)** | Логическая операция к БД, выраженная SQL-подобным текстом. Центральная сущность приложения. |
| **queryId** | Идентификатор запроса на сервере, возвращается при старте; используется во всех последующих вызовах цепочки. |
| **Flow** | Сценарий выполнения запроса: одна из 4 комбинаций (с выборкой / без; direct / non-direct). |
| **QueryFact** | Ответ сервера: `description`, `factNo`, массив `data[]` из `QueryKeyValuePair`. Используется и для статуса, и для строки данных. |
| **QueryKeyValuePair** | Ячейка: `index` (порядковый номер колонки), `key` (имя), `value` (значение). |
| **QueryFactCollection** | Набор `QueryFact` (используется для онтологий — описания колонок). |
| **QueryExecutionStatus** | Статус выполнения, передаётся **внутри `QueryFact.data[]`** парой `key=QueryExecutionStatus`, `value=Executing\|Failed\|Completed`. |
| **Ontology (Онтология)** | В контексте QL — описание колонки результирующей таблицы. |
| **DynaObject** | Динамический объект сервера (проект / калькулятор) с метаданными (статус, размеры, прогресс). |
| **Source (Источник)** | Источник данных (CSV / БД-таблица), который можно просматривать и индексировать. |
| **Tab (Таб)** | Рабочая вкладка приложения. Бывают разных типов; некоторые — в единственном экземпляре; домашний таб закрыть нельзя. |
| **Sidebar / Bottom tab** | Скрываемые панели вокруг основной области; нижняя панель содержит свои табы (контекстные и глобальные). |
| **QueryKind** | Внутренний тип запроса в приложении (enum), на основании которого принимаются решения о подписке/реакции UI. |

## 3. Обзор системы

### 3.1 Сервер и сервисы

Клиент общается с сервером по gRPC. Исторически было **три** gRPC-сервиса; в
production-клиенте останутся **два**:

| Сервис | Proto | Назначение | Судьба |
|---|---|---|---|
| **AuthService** | `auth.api.proto` | Авторизация, профиль пользователя, управление пользователями/группами. | **Остаётся.** |
| **SynapsDbClient** (`DHGDBSharedAPI`) | `dhgdb.shared.api.proto` | Универсальный доступ к данным через **QL** (SQL-подобные запросы) + сервисные методы (ServerVars, ServerInfo, и т.д.). | **Остаётся, ключевой.** |
| ~~DdbsApiClient~~ (`DynamicHyperGraphDB`) | `dhgdb.api.proto` | Старый специализированный API (проекты, граф, CSV, папки — ~74 RPC). | **Выводится из эксплуатации.** |

### 3.2 Почему уходит DdbsApiClient

`SynapsDbClient` спроектирован как **универсальный** клиент на базе QL и способен
**повторить всю функциональность** старого `DdbsApiClient`: операции с проектами,
источниками, метаданными и выборки данных выражаются через SQL-подобные запросы,
проходящие через единый набор QL-эндпоинтов. Поэтому в новом приложении весь доступ
к данным идёт через `SynapsDbClient`, а специализированный старый API не переносится.

> Практическое следствие для архитектуры: слою данных нужен **один** транспорт к
> `DHGDBSharedAPI` и тонкие доменные обёртки поверх QL, а не множество
> специализированных RPC.

### 3.3 Аутентификация

Токен пользователя передаётся **в заголовке** каждого запроса к `DHGDBSharedAPI`
как пара `user-token: <token>` (см. комментарий в `dhgdb.shared.api.proto`). Это
значит: транспортный слой должен уметь прикреплять метаданные к каждому вызову, а
auth-состояние — быть доступно транспорту централизованно.

## 4. Протокол QL

Это сердце взаимодействия с данными. Здесь — формализация для архитектуры; детальная
пошаговая спецификация (поля, коды ошибок, тайминги) выносится в
[03-protocol/ql-flows.md](../03-protocol/ql-flows.md).

### 4.1 QL-эндпоинты

Из `service DHGDBSharedAPI` (`dhgdb.shared.api.proto`):

| RPC | Request → Response | Роль в flow |
|---|---|---|
| `QLProjects` | `QueryRequest → QueryResponse` | Список проектов (частный случай). |
| `QLExecuteDirect` | `QueryRequest → QueryResponse` | Старт **direct**-запроса, возвращает `queryId`. |
| `QLPrepare` | `QueryRequest → QueryResponse` | Подготовка **non-direct**-запроса. |
| `QLExecute` | `QueryRequest → QueryResponse` | Запуск подготовленного запроса. |
| `QLQueryStatus` | `QueryRequest(queryId) → QueryFact` | Статус выполнения; источник `QueryExecutionStatus`. |
| `QLOntologies` | `QueryRequest(queryId) → QueryFactCollection` | Описание колонок результата. |
| `QLFetch` | `QueryRequest(queryId) → QueryFact` | Очередная строка данных; EOF сигнализируется ошибкой. |
| `QLSetCursor` | `QuerySetCursorRequest → QueryResponse` | Перемещение курсора (вперёд/назад/абсолютно). |
| `QLCancelQuery` | `QueryRequest(queryId) → QueryResponse` | Отмена запроса. |
| `QLCloseQuery` | `QueryRequest(queryId) → QueryResponse` | Закрытие запроса (освобождение ресурсов на сервере). |

`QueryRequest` несёт единственное поле `text` — это либо SQL-текст (на старте), либо
`queryId` (в последующих вызовах). `QueryResponse` несёт `queryId`.

### 4.2 Структуры данных

```
QueryKeyValuePair { uint64 index; string key; string value; }
QueryFact         { string description; uint64 factNo; repeated QueryKeyValuePair data; }
QueryFactCollection { repeated QueryFact rows; }
```

- `description` принимает значения вида `data_row`, `project_row`,
  `project_metrix_row` — тип строки.
- **`QueryExecutionStatus` НЕ является отдельным полем.** Он приходит **внутри
  `QueryFact.data[]`** как элемент с `key == "QueryExecutionStatus"` и
  `value ∈ {Executing, Failed, Completed}` (ключ читать **регистронезависимо** —
  так сделано в POC):

  ```json
  { "index": 0, "key": "QueryExecutionStatus", "value": "Executing" }
  ```

- `QLOntologies` возвращает `QueryFactCollection`, из которого извлекается список
  колонок (онтологий) результирующей таблицы.
- `QLFetch` возвращает по одной `QueryFact` со значениями строки; **признак «строк
  больше нет» — это ошибка** ответа (в POC — gRPC `OUT_OF_RANGE`), а не пустой
  результат.

### 4.3 Direct vs Non-direct

- **Direct** — старт через `QLExecuteDirect`. Сервер начинает выполнение сразу;
  статус, как правило, готов к моменту первого `QLQueryStatus`.
- **Non-direct** — старт через пару `QLPrepare` → `QLExecute`. Выполнение может
  быть длительным, поэтому требуется **polling** `QLQueryStatus` до завершения.

> POC для упрощения в обоих случаях стартует через `QLExecuteDirect`; финальное
> решение по `Prepare/Execute` для non-direct — на фазе архитектуры. Принципиально
> для нас отличие direct/non-direct = «статус готов сразу» vs «нужен polling».

### 4.4 Четыре flow

Во всех flow **`QLCloseQuery` вызывается в любом исходе** (успех, ошибка, отмена) —
это обязательный шаг освобождения ресурсов. Polling выполняется с интервалом
(в POC — настраиваемый, по умолчанию ~500 мс).

`QueryExecutionStatus`:
- `Executing` → операция ещё идёт, повторить `QLQueryStatus` через интервал;
- `Failed` → ошибка, перейти к `QLCloseQuery`;
- `Completed` → операция завершена (для flow с выборкой — переходим к онтологиям/строкам).

#### A. Direct без выборки — `executeDirect`

```
1. QLExecuteDirect(SQL) → queryId
2. QLQueryStatus(queryId) → QueryFact          // один раз
3. QLCloseQuery(queryId) → ok
```
Результат: `QueryFact` из шага 2.

#### B. Non-direct без выборки — `execute`

```
1. (QLPrepare/QLExecute или QLExecuteDirect)(SQL) → queryId
2. QLQueryStatus(queryId) → QueryFact           // {1..n} раз: пока status == Executing
3. QLCloseQuery(queryId) → ok
```
Шаг 2 повторяется, пока `QueryExecutionStatus == Executing`. На `Failed`/`Completed` —
выходим из цикла и закрываем запрос.

#### C. Direct с выборкой — `fetchDirect`

```
1. QLExecuteDirect(SQL) → queryId
2. QLQueryStatus(queryId) → QueryFact
3. QLOntologies(queryId) → QueryFactCollection   // только если status == Completed
4. QLFetch(queryId) → QueryFact                  // {1..r} раз, до EOF (ошибка)
5. QLCloseQuery(queryId) → ok
```
Результат: `QueryFact` статуса + таблица (колонки из шага 3, строки из шага 4).
Если статус ≠ `Completed` либо ошибка на шаге 2/3 — шаги 3–4 пропускаются, но
**шаг 5 (CloseQuery) выполняется обязательно**.

#### D. Non-direct с выборкой — `fetch`

```
1. (старт)(SQL) → queryId
2. QLQueryStatus(queryId) → QueryFact            // {1..n} раз: polling как в B
3. QLOntologies(queryId) → QueryFactCollection   // после Completed
4. QLFetch(queryId) → QueryFact                  // {1..r} раз, до EOF
5. QLCloseQuery(queryId) → ok
```
Начало как в B (polling), завершение как в C (онтологии + строки + close).

#### Схема состояний (общая)

```
        ┌──────────┐   start     ┌────────────┐
        │  Execute ├────────────►│ PollStatus │◄──┐ Executing (retry через интервал)
        └──────────┘             └─────┬──────┘───┘
                                       │
                  Failed ◄─────────────┼─────────────► Completed
                     │                 │                  │
                     │          (flow без выборки)  (flow с выборкой)
                     │                 │                  │
                     │                 │           ┌──────▼──────┐
                     │                 │           │  Ontologies │
                     │                 │           └──────┬──────┘
                     │                 │           ┌──────▼──────┐
                     │                 │           │ Fetch loop  │ → EOF
                     │                 │           └──────┬──────┘
                     ▼                 ▼                  ▼
                 ┌────────────────────────────────────────────┐
                 │              CloseQuery (всегда)           │
                 └────────────────────────────────────────────┘
```

### 4.5 Надёжность транспорта

Из POC переносим политику устойчивости (детали — в спецификации):
- **Retry только на транспортные ошибки** (`CANCELLED`, `DEADLINE_EXCEEDED`,
  `UNAVAILABLE`) для безопасных шагов (polling статуса, close). Не ретраим
  семантические (`NOT_FOUND`, `UNAUTHENTICATED`).
- **Экспоненциальный backoff** (в POC: ~1с → 2с → 5с).
- **Отмена** запроса (`QLCancelQuery` + `QLCloseQuery`).
- Опционально — **восстановление** незавершённых запросов после рестарта
  (в POC состояние сохранялось в Hive). Нужно ли это в Qt — см. [§9](#9-открытые-вопросы--кандидаты-в-adr).

## 5. Ключевые архитектурные концепции

### 5.1 Запрос как центральная сущность

Ключевая концепция приложения — **Запрос**. Запрос моделируется как **наблюдаемый
объект с состоянием**, а не как разовый вызов «отправил-получил». Состояние запроса
включает как минимум: фазу (Execute / PollStatus / Ontologies / Fetch / Closing /
Completed / Failed / Cancelled), последний `QueryExecutionStatus`, прогресс (если
есть), ошибку, и — для flow с выборкой — онтологии и поток строк.

За счёт того, что запрос — наблюдаемый объект, **разные части UI могут реагировать
на один и тот же запрос**, не зная деталей его выполнения.

### 5.2 QueryManager

**QueryManager — единая точка, через которую проходят ВСЕ запросы.** Его
ответственность:

- **Реестр активных запросов** (и, опционально, истории).
- **Запуск** запроса по нужному flow (A/B/C/D), управление его жизненным циклом
  (polling, fetch-loop, close, retry, cancel).
- **Типизация запроса — `QueryKind`** (внутренний enum приложения), на основании
  которого принимаются решения о подписке/реакции UI. Примеры: `CreateSourceIndex`,
  `CreateMetadata`, `LoadProject`, `AdhocSql` (технический SQL-экран) и т.д.
- **Семантический ключ подписки (subject).** Помимо `queryId` (технический,
  выдаётся сервером), у запроса есть **семантический ключ**, по которому UI
  подписывается, **не зная `queryId`**:

  ```
  subject = (QueryKind, targetId)
  // напр.: (CreateSourceIndex, "orders.csv")
  //        (LoadProject,       "project-42")
  ```

  Это позволяет любому компоненту спросить QueryManager: «есть ли активный запрос
  по subject (CreateSourceIndex, orders.csv)?» — и подписаться на него.

> В POC прообразом QueryManager служит связка `SynapsDbClient` +
> `SynapsQueryStateManager` (состояние запросов хранилось и наблюдалось через
> `ValueListenable`). В Qt это становится явным, выделенным компонентом доменного
> слоя. Подробнее: [01-concepts/query-and-query-manager.md](../01-concepts/query-and-query-manager.md).

### 5.3 Модель подписки

Нужен механизм, позволяющий **разным блокам приложения реагировать на один запрос**.
Подходящие паттерны:

- **Observer** — наблюдатели (UI-компоненты) подписываются на изменения состояния
  запроса.
- **Publish/Subscribe (topic-based)** — топик = **семантический ключ** (subject из
  §5.2). Издатель — QueryManager; подписчики — любые ViewModel/компоненты. Развязка
  во времени и по ссылкам: подписчику не нужен прямой указатель на запрос.
- **Mediator** — QueryManager выступает посредником между запросами и наблюдателями,
  централизуя маршрутизацию событий.

**Реализация на Qt** ложится на это естественно:
- состояние запроса — `QObject` с `Q_PROPERTY` + `NOTIFY`-сигналами → прямой
  binding в QML;
- широковещательные события по subject — через сигналы QueryManager (или выделенный
  «event bus»; в POC это `ReactiveEventBus`);
- список активных запросов (например, для нижнего таба **Query Logs**) — через
  `QAbstractListModel`, который QML-таблица отображает напрямую.

#### Сквозной пример: «CREATE SOURCE INDEX»

1. На экране просмотра исходника пользователь жмёт **CREATE METADATA**.
2. ViewModel экрана просит QueryManager выполнить запрос
   `CREATE SOURCE INDEX ...` с `QueryKind = CreateSourceIndex` и
   `targetId = <имя исходника>`. Это flow **B/D** (non-direct, есть polling).
3. Пока `QueryExecutionStatus == Executing`, **три разных места** подписаны на один
   subject `(CreateSourceIndex, <исходник>)` и показывают loader:
   - сам экран источника;
   - строка соответствующего файла в списке на главном экране;
   - индикатор на табе этого экрана.
4. По `Completed`/`Failed` все три подписчика одновременно получают обновление и
   убирают loader / показывают результат.

Ни один из трёх наблюдателей не знает `queryId` и не управляет выполнением — они
лишь наблюдают subject. Подробнее: [01-concepts/subscription-model.md](../01-concepts/subscription-model.md).

### 5.4 SQL Query экран как особый QueryKind

Технический экран **SQL Query** (произвольный SQL-подобный запрос из текстового
поля) — обязательная фича, **делается одной из первых**. Его запросы тоже проходят
через QueryManager, но имеют **свой отдельный `QueryKind`** (напр. `AdhocSql`).
Приложение на такие запросы **не реагирует** подписками (никто не рисует лоадеры в
других местах) — результат виден только в самом SQL-табе. Это естественно следует из
модели: нет подписчиков на subject `AdhocSql` извне экрана.

### 5.5 TabManager

Работа в приложении идёт во вкладках. **TabManager** — реестр и владелец состояния
табов:

- **Типы табов** (`TabKind`): домашний, SQL Query, просмотр источника, проект,
  ветка проекта, RDB-проект и т.д.
- **Single-instance** табы (некоторые типы существуют только в одном экземпляре).
- **Неудаляемый домашний таб** — главный экран, всегда один, закрыть нельзя.
- **Активный таб**, переключение, переименование, дублирование, закрытие.
- **Персистенция** между запусками (в POC — Hive; в Qt — см. [§9](#9-открытые-вопросы--кандидаты-в-adr)).
- У таба может быть **индикатор активности запроса** (через подписку на subject —
  см. пример §5.3) и выбранный нижний таб.

> Прообраз — `TabsRepository` / `TabsBloc` / `TabManagerEntity` из POC. TabManager
> переносится как архитектурный шаблон и проектируется как явный компонент.
> Подробнее: [01-concepts/tab-manager.md](../01-concepts/tab-manager.md).

### 5.6 Разделение слоёв (MVVM)

Главная боль POC — перемешанные слой отображения и слой данных. В Qt-клиенте это
разводится жёстко по модели **MVVM**:

```
Presentation (QML)              — только отображение и ввод; бизнес-логики нет
        ▲ Q_PROPERTY / signals / Q_INVOKABLE
ViewModel (C++ QObject)         — состояние экрана, реакция на ввод, подписки
        ▲
Application / Domain            — QueryManager, TabManager, доменные сервисы (Auth,
                                  Source, Project), QueryKind, subjects
        ▲
Data / Transport                — gRPC-клиенты (Auth, DHGDBSharedAPI), маппинг
                                  proto↔домен, персистенция; никакого QML/UI
```

Жёсткие правила:
- В QML **нет** бизнес-логики и прямых вызовов транспорта.
- В слое данных **нет** ничего про представление (никаких QML-типов, цветов,
  лейаутов).
- ViewModel — **граница**: переводит доменные события в свойства/сигналы для QML и
  пользовательский ввод — в доменные команды.

Подробнее: [01-concepts/layering-and-mvvm.md](../01-concepts/layering-and-mvvm.md).

## 6. Требования

### 6.1 Функциональные

| # | Требование |
|---|---|
| F1 | Авторизация через `AuthService` (login, восстановление сессии, logout); токен подкладывается в header `user-token` ко всем вызовам `DHGDBSharedAPI`. |
| F2 | Все обращения к данным идут через `SynapsDbClient` (QL); старый `DdbsApiClient` не используется. |
| F3 | Поддержка всех **4 flow** (`executeDirect`, `execute`, `fetchDirect`, `fetch`) с корректным polling, выборкой (онтологии + строки), отменой и обязательным `QLCloseQuery`. |
| F4 | Все запросы проходят через **QueryManager** с присвоением `QueryKind` и семантического ключа (subject). |
| F5 | **Модель подписки**: несколько мест UI реагируют на один запрос (лоадеры на экране, в списке, на табе) по subject, не зная `queryId`. |
| F6 | Технический **SQL Query** экран (произвольный запрос, выбор flow/режима, таблица результатов, queryId/статус); отдельный `QueryKind`, без внешних реакций. **Приоритет — в первую очередь.** |
| F7 | **Табы**: создание/закрытие/переключение/переименование/дублирование; типы табов; single-instance; неудаляемый домашний таб; индикатор активности запроса на табе. |
| F8 | **4-панельный layout**: основная область + левый/правый контекстные скрываемые сайдбары + нижний скрываемый сайдбар с табами (контекстные, напр. Metrix, и глобальные, напр. Query Logs). |
| F9 | Нижний таб **Query Logs** показывает список активных/исторических запросов (поверх реестра QueryManager). |
| F10 | Просмотр источника с действиями **CREATE METADATA / CREATE SOURCE INDEX** (длительные запросы flow B/D с лоадерами по подписке). |
| F11 | **Персистенция** открытых табов между запусками. |
| F12 | **Отмена** выполняющегося запроса из UI. |
| F13 | (Опц.) **Восстановление** незавершённых запросов после рестарта — решается в [§9](#9-открытые-вопросы--кандидаты-в-adr). |

### 6.2 Нефункциональные

| # | Требование |
|---|---|
| N1 | **Кроссплатформенность**: Windows, macOS, Linux (desktop). |
| N2 | **Неблокирующий UI**: все сетевые/долгие операции асинхронны, UI-поток не блокируется (polling, fetch-loop, retry). |
| N3 | **Надёжность транспорта**: retry на транспортные ошибки с backoff; корректная обработка семантических ошибок и отмен. |
| N4 | **Расширяемость**: добавление нового экрана / нового `QueryKind` / нового нижнего таба не требует переписывания ядра. |
| N5 | **Тестируемость**: слои данных и домена тестируются без UI (QueryManager/TabManager — модульно; gRPC мокируется, есть `synaps_mock_server`). |
| N6 | **Чистое разделение слоёв** (MVVM) — отсутствие бизнес-логики в QML и представления в данных. |
| N7 | **i18n**: исходный язык UI — **английский** (см. `synaps_client/CLAUDE.md`); локализация через механизм Qt позже. |
| N8 | **Диагностика**: структурированное логирование, наблюдаемость запросов (Query Logs), сообщения об ошибках. |
| N9 | **Визуальный язык** наследуется из POC (`app_style.dart` → `Theme.qml`). |

## 7. Рекомендуемое направление архитектуры

> Это **направление**, а не финальный дизайн. Конкретные классы, интерфейсы и
> сигнатуры — задача фазы архитектуры.

### 7.1 Слои и крупные компоненты

```
┌──────────────────────────── Presentation (QML) ─────────────────────────────┐
│  Main · Layout(4 панели) · экраны (SQL Query, Source Preview, Home, ...)    │
│  Bottom-tabs (Metrix, Query Logs, ...) · общие компоненты (таблицы, лоадеры)│
└───────────────▲──────────────── Q_PROPERTY / signals / Q_INVOKABLE ─────────┘
                │
┌───────────────┴──────────────── ViewModel (C++ QObject) ────────────────────┐
│  по одному VM на экран/панель; подписки на subjects; состояние экрана       │
└───────────────▲─────────────────────────────────────────────────────────────┘
                │
┌───────────────┴──────────────── Application / Domain ───────────────────────┐
│  QueryManager (реестр, flow-движок, QueryKind, subjects)                    │
│  Query (наблюдаемый объект состояния)                                       │
│  TabManager (реестр табов, типы, single-instance, активный)                 │
│  Доменные сервисы: Auth, Source, Project (тонкие обёртки над QL)            │
└───────────────▲─────────────────────────────────────────────────────────────┘
                │
┌───────────────┴──────────────── Data / Transport ───────────────────────────┐
│  SynapsTransport → DHGDBSharedAPI (gRPC) · AuthTransport → Auth (gRPC)      │
│  маппинг proto↔домен · header user-token · QueryStore (персистенция)        │
└─────────────────────────────────────────────────────────────────────────────┘
```

Ответственность ключевых компонентов:

| Компонент | Ответственность |
|---|---|
| **AuthService** | Логин/сессия/профиль; владеет токеном; уже есть в каркасе (расширить под gRPC). |
| **SynapsTransport** | Единственный канал к `DHGDBSharedAPI`; прикрепляет `user-token`; преобразует RPC ↔ домен. |
| **QueryManager** | Запуск/жизненный цикл запросов по flow; реестр; `QueryKind`; маршрутизация событий по subjects. |
| **Query** | Наблюдаемое состояние одной операции (фаза/статус/прогресс/ошибка/онтологии/строки). |
| **QueryStore** | Персистенция/история запросов (если нужна); источник для Query Logs. |
| **TabManager** | Реестр и состояние табов; правила (single-instance, неудаляемый home). |
| **Screen ViewModels** | Состояние конкретного экрана; подписки; перевод ввода в доменные команды. |
| **Layout / Bottom-tabs registry** | 4-панельная оболочка; реестр нижних табов (контекстные/глобальные). |

### 7.2 Технологические рекомендации

- **Qt 6 + QML**, C++20, CMake/Ninja (как в каркасе). Регистрация C++-типов в QML —
  как у текущего `AuthService` (`QML_ELEMENT`/`QML_SINGLETON`/`Q_PROPERTY`/
  `Q_INVOKABLE`/`Q_ENUM`).
- **MVVM** как основной паттерн связки C++↔QML.
- **gRPC: рекомендуется QtGrpc + QtProtobuf** (нативно ложится на QObject/сигналы,
  упрощает async и связку с QML). **Это открытый вопрос** — финальный выбор между
  QtGrpc и raw `grpc++` фиксируется в [adr/0001-grpc-stack.md](../adr/0001-grpc-stack.md).
- **Async-модель** (Qt-корутины vs callbacks vs worker-threads) — решается в фазе
  архитектуры (см. [§9](#9-открытые-вопросы--кандидаты-в-adr)); требование N2 (не
  блокировать UI) обязательно.
- **Персистенция**: `QSettings` для простого состояния (сессия, размеры панелей),
  **SQLite** или файловый стор для табов/истории запросов — выбрать в фазе архитектуры.
- **Модели для списков** (Query Logs, метрики, таблицы данных) — `QAbstractListModel`/
  `QAbstractTableModel`.
- **Тесты**: модульные для QueryManager/TabManager; интеграционные против
  `synaps_mock_server`.

### 7.3 Маппинг POC → Qt

| POC (Flutter) | Qt-клиент |
|---|---|
| `SynapsDbClient` + `SynapsQueryStateManager` | **QueryManager** + **Query** + **QueryStore** |
| `*Bloc` (state management) | **ViewModel** (C++ QObject) |
| `*Repository` (бизнес-логика) | доменные сервисы + ViewModel |
| `*Service` (gRPC) | **SynapsTransport** / **AuthService** (Data-слой) |
| `ReactiveEventBus` | сигналы QueryManager / выделенный event-bus (по subjects) |
| `TabsRepository` / `TabsBloc` / `TabManagerEntity` | **TabManager** + модели табов |
| `*Entity` (freezed-модели) | доменные структуры C++ / QML-доступные модели |
| `screens/*`, `widgets/layout/*` | QML-экраны и QML Layout (4 панели) |
| `app_style.dart` | **Theme.qml** (уже начато) |
| Hive (персистенция) | QSettings / SQLite (по виду данных) |

## 8. Структура экрана и навигация

### 8.1 Анатомия таба (4 части)

```
┌───────────────────────────── строка табов (вверху) ───────────────────┐
├───────────┬───────────────────────────────────────────────┬───────────┤
│ ЛЕВЫЙ     │                                               │ ПРАВЫЙ    │
│ сайдбар   │ ОСНОВНАЯ ОБЛАСТЬ                              │ сайдбар   │
│ (скрыв.,  │ (отображение и работа с данными)              │ (скрыв.,  │
│ контекст) │                                               │ контекст) │
├───────────┴───────────────────────────────────────────────┴───────────┤
│ НИЖНИЙ сайдбар (скрываемый) — табы: [Metrix] [Query Logs] [Logs] ...  │
└───────────────────────────────────────────────────────────────────────┘
```

- **Основная область** — отображение и работа с данными конкретного экрана.
- **Левый / правый сайдбары** — скрываемые, **контекстно-зависимые** (содержимое
  зависит от типа экрана).
- **Нижний сайдбар** — скрываемый, со своими **табами**:
  - **контекстные** (зависят от типа экрана, напр. **Metrix**);
  - **глобальные** (не зависят от экрана, напр. **Query Logs** — поверх реестра
    QueryManager).

Прообраз — `widgets/layout/` из POC (`layout_panel_{top,left,right,bottom}_widget`,
`layout_tabs_widget`). В каркасе `synaps_client/HomePage.qml` уже есть набросок
скрываемых панелей с перетаскиванием границ.

### 8.2 Экраны (из POC)

Детальная проработка каждого экрана — отдельная задача. Список для ориентира:

| Экран | Назначение | Приоритет |
|---|---|---|
| **SQL Query** | Произвольный SQL-подобный запрос, выбор flow/режима, таблица результатов, queryId/статус. | **Первый** |
| **Home** (главный) | Список проектов/источников/CSV; неудаляемый домашний таб. | Высокий |
| **Source Preview** | Просмотр таблиц источника; **CREATE METADATA / CREATE SOURCE INDEX**; правила, ключи. | Высокий |
| **Project** | DDB-проект: граф + схема, метрики. | Средний |
| **Project Branch** | Ветка проекта (подмножество узлов). | Средний |
| **RDB Project** | RDB-проект: таблицы/данные. | Средний |
| **Login** | Авторизация. | Готово (каркас) |
| **Error / Loading** | Системные состояния. | По мере надобности |
